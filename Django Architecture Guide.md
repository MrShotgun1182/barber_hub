# Django & Tailwind Architecture Guide: Technical Structure & Design Standards

This document establishes the standard for directory structure, layering, frontend management, and naming conventions in Django projects. The goal of this architecture is complete Separation of Concerns (SoC), code simplicity through standalone function methodology, and modern integration of frontend tools.

## 1. Project Directory Tree

The overall structure of the project is divided into three main sections:
1. **`core`**: Root and core settings of Django.
2. **`apps`**: Modular backend apps and layers of the project.
3. **`frontend`**: An independent environment for frontend tooling (NPM, raw static files, and Tailwind configuration).

```text
my_project/
│
├── core/                         # Core project configuration
│   ├── __init__.py
│   ├── settings.py
│   └── urls.py
│
├── apps/                         # Reference folder for all backend apps & layers
│   │
│   └── accounts/                 # Example application (e.g., user management)
│       ├── __init__.py
│       ├── apps.py
│       │
│       ├── models/               # Database models directory
│       │   ├── __init__.py
│       │   └── account_model.py
│       │
│       ├── views/                # Django views directory (PascalCase functions)
│       │   ├── __init__.py
│       │   └── home_view.py
│       │
│       ├── actions/              # Action layer (orchestration between view and service)
│       │   ├── __init__.py
│       │   └── user_login_action.py
│       │
│       ├── services/             # Database access and business logic functions layer
│       │   ├── __init__.py
│       │   └── get_account_service.py
│       │
│       └── templates/            # App-local template folder
│           └── accounts/         # Subfolder named after app to prevent name collisions
│               └── home.html
│
├── frontend/                     # Independent frontend layer & Tailwind management
│   ├── node_modules/             # Installed npm packages
│   ├── src/                      # Raw CSS files & input styles for Tailwind
│   │   └── input.css
│   ├── package.json              # Compilation scripts for Tailwind
│   └── tailwind.config.js        # Custom Tailwind configuration
│
├── static/                       # Final compiled static output (final CSS files)
│   └── css/
│       └── output.css            # Compiled CSS generated by Tailwind, loaded in templates
│
├── templates/                    # Global project templates directory (e.g., base.html)
│   └── base.html
│
└── manage.py
```

## 2. System Pathing and Template Settings (`settings.py`)

To remove the redundant prefix `apps.` when registering and referencing apps, manage global templates, and route compiled Tailwind static files, configure `settings.py` as follows:

```python
import sys
from pathlib import Path

# Project root directory
BASE_DIR = Path(__file__).resolve().parent.parent

# Add apps directory to sys.path for direct app imports
sys.path.insert(0, str(BASE_DIR / 'apps'))

INSTALLED_APPS = [
    'django.contrib.admin',
    'django.contrib.auth',
    'django.contrib.contenttypes',
    'django.contrib.sessions',
    'django.contrib.messages',
    'django.contrib.staticfiles',
    
    # Project applications registered without the 'apps.' prefix
    'accounts',  
]

TEMPLATES = [
    {
        'BACKEND': 'django.template.backends.django.DjangoTemplates',
        # Global templates directory in project root (for files like base.html)
        'DIRS': [BASE_DIR / 'templates'],
        # Enable automatic discovery of templates/ folder inside each application
        'APP_DIRS': True,
        'OPTIONS': {
            'context_processors': [
                'django.template.context_processors.debug',
                'django.template.context_processors.request',
                'django.contrib.auth.context_processors.auth',
                'django.contrib.messages.context_processors.messages',
            ],
        },
    },
]

# Static files settings for reading compiled Tailwind output
STATIC_URL = 'static/'
STATICFILES_DIRS = [
    BASE_DIR / 'static',
]
```

## 3. Naming Conventions for Files and Functions

* **File Names (snake_case):** All filenames must be lowercase and suffix-suffixed with the corresponding layer name matching its directory (`_service`, `_action`, or `_view`).
* **Entry Functions (PascalCase):** Inside views, actions, and services files, the main entry-point function is defined in `PascalCase` to stand out from internal helper functions.

### Naming Reference Table:

| Layer (Directory) | File Naming Rule (snake_case) | Main Function/Class Naming Rule | Sample File Path & Entry Function |
| --- | --- | --- | --- |
| **Models** | `[name]_model.py` | `[Name]Model` (Django Model Class) | `account_model.py` / `AccountModel` |
| **Services** | `[action]_[name]_service.py` | `[Action][Name]Service` (Entry Function) | `get_account_service.py` / `GetAccountService` |
| **Actions** | `[operation]_[name]_action.py` | `[Operation][Name]Action` (Entry Function) | `user_login_action.py` / `UserLoginAction` |
| **Views** | `[name]_view.py` | `[Name]View` (Entry Function) | `home_view.py` / `HomeView` |
| **Templates** | `[name].html` | — | `templates/accounts/home.html` |

## 4. Tailwind CSS Configuration in Frontend Directory

To allow the frontend layer to monitor and compile utility classes used in HTML files across both global templates and application-level templates, configure `frontend/tailwind.config.js` as follows:

```javascript
/** @type {import('tailwindcss').Config} */
module.exports = {
  content: [
    // Watch project root templates
    "../templates/**/*.html",
    // Watch all app templates inside apps directory
    "../apps/**/templates/**/*.html",
    // Watch frontend JavaScript files if any
    "./src/**/*.js",
  ],
  theme: {
    extend: {},
  },
  plugins: [],
}
```

> **Build Note:** In `frontend/package.json`, set the build script so that compiled CSS output is generated directly into the project root's `static` directory:  
> `"build": "tailwindcss -i ./src/input.css -o ../static/css/output.css --watch"`

## 5. Implementation Code Flow & Examples

### A) Service Layer (`apps/accounts/services/get_account_service.py`)

```python
from accounts.models.account_model import AccountModel

def GetAccountService(account_id: int) -> AccountModel | None:
    """
    Pure Service Layer function for querying account data from the database.
    """
    try:
        return AccountModel.objects.get(id=account_id)
    except AccountModel.DoesNotExist:
        return None
```

### B) Authentication Service Layer (`apps/accounts/services/authenticate_user_service.py`)

```python
from django.contrib.auth import authenticate

def AuthenticateUserService(username: str, password: str):
    """
    User authentication service layer function.
    """
    user = authenticate(username=username, password=password)
    return user
```

### C) Action Layer (`apps/accounts/actions/user_login_action.py`)

```python
from accounts.services.get_account_service import GetAccountService
from accounts.services.authenticate_user_service import AuthenticateUserService
from django.contrib.auth import login

def UserLoginAction(request, username: str, password: str) -> dict:
    """
    Action Layer function orchestrating the user login process.
    Combines multiple services to perform a single cohesive business operation.
    """
    result = {
        'success': False,
        'user': None,
        'account': None,
        'error': None
    }
    
    # 1. Authenticate user via service
    user = AuthenticateUserService(username, password)
    
    if user is not None:
        # 2. Log user into current session
        login(request, user)
        
        # 3. Fetch full account profile details
        account_data = GetAccountService(user.id)
        
        result['success'] = True
        result['user'] = user
        result['account'] = account_data
    else:
        result['error'] = 'Invalid username or password.'
    
    return result
```

### D) View Layer (`apps/accounts/views/login_view.py`)

```python
from django.shortcuts import render, redirect
from accounts.actions.user_login_action import UserLoginAction

def LoginView(request):
    """
    View Layer function handling user login HTTP requests.
    Views only invoke Actions and avoid direct calls to Services or ORM models.
    """
    if request.method == 'POST':
        username = request.POST.get('username')
        password = request.POST.get('password')
        
        # Invoke login Action — business logic is encapsulated in Action
        result = UserLoginAction(request, username, password)
        
        if result['success']:
            return redirect('home')
        else:
            context = {
                'error': result['error']
            }
            return render(request, 'accounts/login.html', context)
    
    return render(request, 'accounts/login.html')
```

### E) Dashboard View Layer (`apps/accounts/views/home_view.py`)

```python
from django.shortcuts import render
from accounts.actions.get_user_dashboard_action import GetUserDashboardAction

def HomeView(request):
    """
    View Layer function handling request routing and rendering dashboard templates.
    """
    # Call Action layer to retrieve dashboard data
    dashboard_data = GetUserDashboardAction(request.user)
    
    context = {
        'dashboard': dashboard_data
    }
    
    # Render view using app namespaced template structure
    return render(request, 'accounts/home.html', context)
```

### F) Global Master Template (`templates/base.html`)

All app templates inherit from this file, loading the final output compiled CSS from Tailwind:

```html
{% load static %}
<!DOCTYPE html>
<html lang="en" dir="ltr">
<head>
    <meta charset="UTF-8">
    <title>{% block title %}My Project{% endblock %}</title>
    <link rel="stylesheet" href="{% static 'css/output.css' %}">
</head>
<body class="bg-gray-100 text-gray-900">
    {% block content %}
    {% endblock %}
</body>
</html>
```

## 6. Action Layer Detailed Overview

The Action Layer sits as an intermediary orchestration layer between Views and Services, responsible for:

### 6.1. Service Orchestration
- Coordinating calls across multiple distinct services to execute a unified business process.
- Managing execution order, data dependencies, and parameter hand-offs between services.

### 6.2. Business Logic Encapsulation
- Implementing complex business rules requiring multi-step processing.
- Providing a single, consistent entry point for business execution.

### 6.3. Transaction Management
- Controlling atomic database transactions (`transaction.atomic`) at the action level.
- Guaranteeing data integrity across multi-step mutations.

### 6.4. Key Architecture Benefits:
- **Simplified Views:** Views contain minimal glue code, calling only a single Action.
- **High Reusability:** Actions can be invoked across different views, API endpoints, CLI commands, or Celery tasks.
- **Improved Testability:** Business workflows can be easily isolated and unit-tested independently of HTTP requests.
- **Clear Boundaries:** Data flow, operational boundaries, and responsibility separations remain explicit and maintainable.
