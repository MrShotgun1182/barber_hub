# اسکیل: کامیت تمیز و مدیریت Git

این اسکیل بر اساس سند «Standard Guide for Using Git and Maintaining a Clean Commit History» (در ریشه پروژه) ساخته شده است.
هر وقت قرار است تغییرات را کامیت کنی یا پیام کامیت بنویسی، طبق این اسکیل عمل کن.

## قوانین طلایی

1. **`git add .` مطلقاً ممنوع است.** فایل‌ها را صریح و هدفمند انتخاب کن:
   - فایل واحد: `git add path/to/file.py`
   - چند فایل مرتبط: `git add path/to/file1.py path/to/file2.py`
   - کل دایرکتوری فقط وقتی همه تغییراتش یک هدف دارند: `git add path/to/module/` — و قبلش محتوایش را با `git status` و `git diff` بررسی کن.
2. هر کامیت **یک هدف مشخص** دارد: فایل‌های یک تغییرِ واحد با هم کامیت می‌شوند؛ تغییرات بی‌ربط (حتی هم‌زمان انجام‌شده) در کامیت‌های جدا.
3. گروه‌بندی بر اساس **هدفِ تغییر** است، نه محل فایل‌ها. مدل + سرویس + اکشن + ویو + تستِ یک قابلیت = یک کامیت منطقی.
4. فایل‌های موقت، خروجی تولیدی، اطلاعات محرمانه (`.env`، کلیدها، پسوردها) هرگز وارد کامیت نشوند؛ در صورت نیاز قاعده‌شان را به `.gitignore` اضافه کن.
5. قبل از هر کامیت، محتوای Stage شده را با `git diff --staged` حتماً بازبینی کن (این گام اجباری است).
6. تاریخچه کامیت‌های push شده مشترک را بدون هماهنگی با تیم بازنویسی نکن.

## فرآیند استاندارد هر کامیت (به ترتیب)

۱. `git status` — وضعیت مخزن: تغییرات، فایل‌های جدید، وضعیت Stage.
۲. `git diff` (یا `git diff -- path/to/file.py`) — بازبینی محتوای تغییرات.
۳. `git add <فایل‌های مرتبط>` — انتخاب صریح فایل‌ها.
۴. `git diff --staged` (و `git diff --staged --name-only`) — بازبینی دقیق آنچه قرار است کامیت شود.
   - اگر فایل بی‌ربطی وارد Stage شده: `git restore --staged path/to/file.py` (فقط از Stage خارج می‌کند؛ تغییرات فایل دست نمی‌خورد).
۵. `git commit -m "<type>(<scope>): <description>"` — ثبت کامیت با پیام استاندارد.
۶. `git status` — بررسی نتیجه و تغییرات باقی‌مانده.

## پیام کامیت (Conventional Commits)

ساختار: `<type>(<scope>): <description>`

- **scope** اختیاری است: نام کوتاه و مشخص بخش پروژه (`booking`, `barbers`, `store`, `frontend`, `api`, ...).
- **description**:
  - انگلیسی، کوتاه، دقیق، ترجیحاً امری (imperative).
  - حرف اول کلمه اول کوچک؛ **بدون نقطه در انتها**.
  - باید بگوید **چه چیزی تغییر کرده**، نه اینکه «کاری انجام شده».
  - پیام‌های مبهم مثل `fix bug`، `update files`، `changes`، `final update` ممنوع.

انواع مجاز:

| type | کاربرد |
|---|---|
| `feat` | قابلیت جدید |
| `fix` | رفع باگ |
| `refactor` | بازسازی کد بدون تغییر رفتار |
| `docs` | تغییر مستندات |
| `test` | افزودن/تغییر تست |
| `style` | تغییر قالب کد بدون تغییر منطق |
| `perf` | بهبود کارایی |
| `build` | تغییر سیستم بیلد یا وابستگی‌ها |
| `ci` | تغییر CI/CD |
| `chore` | کارهای عمومی نگهداری |

نوع کامیت را بر اساس **هدف اصلی تغییر** انتخاب کن، نه نوع فایل.

نمونه‌های درست: `feat(booths): prevent duplicate reservations` · `fix(auth): handle expired access tokens` · `docs(setup): clarify installation instructions`

## اندازه کامیت

- کامیت‌ها کوچک، مستقل و معنادار؛ اما کوچک یعنی «هر فایل یک کامیت» نیست.
- تغییراتی که با هم یک واحد منطقی کامل می‌سازند (مثل اعتبارسنجی + سرویس + تست‌هایش) در **یک** کامیت.
- چند کارِ هم‌زمان با اهداف متفاوت = چند کامیت مستقل.

## فایل‌های جدید/حذف/تغییرنام

- وضعیت‌ها را با `git status --short` ببین.
- حذف یا تغییر فایل‌های ردیابی‌شده: `git add -u path/to/file.py` (فایل جدید اضافه نمی‌کند).
- تغییر نام: `git mv old_name.py new_name.py` — تغییرنام‌های گسترده را با تغییرات بی‌ربط در یک کامیت ترکیب نکن.

## مدیریت خطا

- فایل اشتباهی Stage شده: `git restore --staged path/to/file.py`
- برگرداندن تغییرات unstaged یک فایل به آخرین کامیت (بعد از بازبینی دقیق، مخرب است): `git restore path/to/file.py`
- افزودن فایل فراموش‌شده به آخرین کامیتِ push نشده (فقط اگر همان هدف را دنبال می‌کند): `git commit --amend`

## چک‌لیست قبل از هر کامیت

- [ ] هدف کامیت مشخص است.
- [ ] فقط فایل‌های هم‌هدف Stage شده‌اند.
- [ ] `git add .` استفاده نشده.
- [ ] `git diff --staged` بازبینی شده.
- [ ] فایل محرمانه/موقت/بی‌مصرف داخل کامیت نیست.
- [ ] تست‌های مرتبط در صورت لزوم اجرا شده‌اند.
- [ ] پیام کامیت طبق ساختار Conventional Commits است.
- [ ] تغییرات مستقل در کامیت‌های جدا هستند.

## نکته درباره این پروژه

تاریخچه فعلی این ریپو پیام‌هایی مثل `i dont now` و `work on barberShop store` دارد — دقیقاً همان چیزی که این سند منع می‌کند. از این به بعد همه کامیت‌های این پروژه (از جمله کامیت‌هایی که خودم می‌سازم) باید طبق این اسکیل باشند.
